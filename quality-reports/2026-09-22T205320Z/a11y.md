# a11y — 2026-09-22T205320Z

**Verdict:** not-ready against WCAG 2.2 AA · **Confidence:** medium · **Regression vs cce584c:** none (no frontend diff)

A keyboard-only user can finish the whole journey: log in, create, open, edit, delete, filter, sort and log out. Getting through it is harder than it should be:
- Modals do not hold focus.
- Focus drops to `<body>` after almost every action.
- At 320 px the header runs off-screen.

A screen-reader user gets the wrong role for the search field and for the table rows, and cannot tell which Open/Closed filter is selected. Every severity badge fails text contrast. None of these is new in this candidate.

## What passed

- Every control is reachable and operable by keyboard.
- Rows open with Enter or Space.
- Both modals have `role=dialog`, `aria-modal`, an accessible name taken from the heading, a labelled Close button, and Escape to close.
- Initial focus goes to the Title field.
- Form fields have associated labels.
- Errors use `role=alert`.
- `aria-sort` is correct and the sort arrow is `aria-hidden`.
- Severity is shown as text as well as colour.
- `lang="en"` is set.
- /login reflows at 320 px.

## Not run / manual checks still needed

- axe-core is not installed, so it was not run.
- No real screen reader was driven. Someone still needs to check these with VoiceOver/Safari and NVDA/Firefox:
  - how the search field is announced
  - how the table rows are read
  - the Open/Closed state
  - dialog entry, and the virtual cursor with two aria-modal dialogs
  - whether sort, filter and save changes are announced
- Only Chromium was used; Firefox and WebKit were not tested.
- 400% zoom was tested with a 320 px viewport, not real browser zoom.
- Not checked: text spacing (1.4.12), forced-colors mode, touch.
